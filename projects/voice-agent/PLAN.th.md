## เป้าหมาย

คนเปิดเว็บแอป (หรือหน้าเฉพาะ) แล้วกดปุ่ม "โทร" เพื่อเริ่มบทสนทนาด้วยเสียงสดกับ AI agent —
ไม่มีเบอร์โทรเข้าสำหรับ V1 agent ตอบคำถาม, พาไปตามหัวข้อที่ scripted ไว้, หรือช่วยทำงาน
ทั้งหมดผ่านเสียงล้วนๆ ไม่ต้องมีทางเลือกเป็นข้อความสำรองระหว่างคุย
คำแนะนำ: **โทรผ่านเบราว์เซอร์ ไม่ใช่เบอร์โทรศัพท์** เพราะการโทรผ่านเบราว์เซอร์ไม่ต้อง
จัดหาระบบ telephony, ไม่ต้องมีบัญชี PSTN, และให้เราปรับปรุง pipeline หลัง feature flag
ได้ก่อนที่จะผูกมัดกับค่าใช้จ่าย carrier และภาระ support ของเบอร์โทรสาธารณะ

## ขอบเขต V1: WebRTC (เบราว์เซอร์) ไม่ใช่ SIP/PSTN

- **ช่องทาง: โทรผ่านเบราว์เซอร์ด้วย WebRTC** ผ่านปุ่ม "โทร" ในเว็บแอป (น่าจะอยู่ที่ `web/`
  หรือ route ใหม่) เหตุผล: prototype ได้เร็วที่สุด ไม่ต้องจัดหา vendor/เบอร์โทร telephony,
  การเข้าถึง mic/speaker ของเบราว์เซอร์เป็นปัญหาที่แก้แล้ว และวิศวกรทดสอบเองได้ทั้งหมด
  โดยไม่ต้องมีสายโทรศัพท์ภายนอก
- SIP/PSTN (เบอร์โทรเข้าจริง) เป็นช่องทางแยกที่เลื่อนไป V2+ — latency profile ต่างกัน,
  การจัดการ interruption/jitter ต่างกัน, และต้องเชื่อม vendor ของตัวเอง (Twilio/Telnyx ฯลฯ)

## สิ่งที่ไม่ทำใน V1 (ชัดเจน)

- เบอร์โทร / PSTN / SIP trunking ทุกรูปแบบ
- รองรับหลายภาษา (V1 ใช้ภาษาเดียว น่าจะเป็นอังกฤษ)
- โทรออก (agent โทรหาคน) — V1 รับสายที่ผู้ใช้เริ่มเองเท่านั้น
- โอนสายไปหาคนจริง / warm transfer (เป็นเรื่องของ V2 — ดูคำถามเปิด)
- คุยหลายฝ่ายพร้อมกัน (V1 คือคน 1 + agent 1 เท่านั้น)
- ความจำเสียง/personalization ข้ามการโทรแต่ละครั้ง (อยู่นอกขอบเขตของ pipeline นี้)
- การเชื่อมแอปมือถือ native (V1 เล็งไปที่เบราว์เซอร์บนเดสก์ท็อป/มือถือเท่านั้น)

## ส่วนประกอบหลักของ Pipeline

1. **VAD (voice activity detection)** — ตรวจว่าคนเริ่ม/หยุดพูดเมื่อไหร่ เพื่อให้ pipeline
   รู้ว่าต้องเริ่ม stream ไปที่ STT เมื่อไหร่ และเทิร์นจบเมื่อไหร่ ทำงานฝั่ง client หรือที่
   ขอบของการรับข้อมูล เพื่อไม่ต้อง stream ความเงียบ
2. **Streaming STT** — แปลงเสียงเป็นข้อความแบบทยอย (มีทั้ง partial และ final transcript)
   ไม่ใช่รอครบความเงียบแล้วค่อย batch เพื่อให้ LLM เริ่มคิดได้ก่อนคนพูดจบ
3. **ขั้นตอน LLM ตัดสินใจพูด/ตอบ** — ตัดสินใจว่าจะตอบเมื่อไหร่ (เมื่อ VAD บอกเทิร์นจบ +
   STT ให้ final transcript) แล้วสร้างคำตอบ ตรงนี้เป็นจุดที่ **barge-in / การจัดการถูกขัด**
   อยู่ด้วย: ถ้า VAD ตรวจเจอเสียงพูดใหม่ระหว่าง TTS กำลังเล่นอยู่ pipeline ต้องยกเลิก/
   ลดเสียง TTS ปัจจุบันทันที แล้วส่ง input ใหม่กลับไปที่ STT — การจัดการ interruption
   เป็นเรื่องข้ามส่วนที่แตะทั้ง VAD, ขั้นตอน LLM (ยกเลิกการ generate ที่ค้างอยู่),
   และ TTS (หยุดเล่น) ไม่ใช่ component เดี่ยวๆ
4. **Streaming TTS** — สังเคราะห์คำตอบของ LLM เป็นเสียงแบบทยอย (ทีละประโยคหรือ
   token-stream-to-audio) เพื่อให้เริ่มเล่นเสียงได้ก่อนคำตอบเต็มถูกสร้างเสร็จ

รูปร่าง pipeline: `mic → VAD → streaming STT → LLM (ตัดสินใจพูด + ยกเลิกเมื่อถูกขัด) →
streaming TTS → ลำโพง` พร้อม feedback loop จาก VAD กลับไปที่ขั้นตอน LLM/TTS
สำหรับกรณีถูกขัด

## งบประมาณ Latency

**เป้าหมาย: ~1.5 วินาที round-trip** (คนหยุดพูด → เสียงของ agent เริ่มเล่น)
ตรงกับเกณฑ์ของ persona เองที่ว่า "~1-2 วินาทีไม่งั้นจะไม่รู้สึกเหมือนคุยกันจริง"
สิ่งนี้จำกัดการออกแบบ:
- ห้ามมี agent chain แบบหลายสเต็ปที่ช้า (เรียก tool, retrieval หลายรอบ, คิดนาน)
  เกิดขึ้นแบบ synchronous ระหว่างเทิร์น — อะไรที่เกินประมาณ 1 วินาทีต้องมีคำพูดคั่นเวลา
  ("เดี๋ยวนะครับ ขอเช็คก่อน...") ระหว่างที่งานทำต่อเบื้องหลัง หรือต้องเลื่อนไป V2
- ตัด LLM ขนาดใหญ่/ช้าออกจากเทิร์นสนทนาหลัก เว้นแต่จะจับคู่กับการ generate แบบ
  speculative/streaming; เลือกโมเดลเล็กกว่าหรือ optimize จัดมาแล้วสำหรับ hot path
- ทั้ง STT และ TTS ต้อง streaming-first ไม่ใช่ request/response เพราะแค่ตัวใดตัวหนึ่ง
  ที่เป็น blocking call เดียวก็กินงบเวลาทั้งหมดได้แล้ว

## Build vs Buy

- **แพลตฟอร์ม voice-agent สำเร็จรูป** (เช่น Vapi, Retell, Bland หรือคล้ายกัน):
  ส่งมอบเร็วที่สุด จัดการ VAD/STT/TTS/turn-taking/interruption ให้พร้อมใช้
  Trade-off: ควบคุม latency tuning และสลับ component แต่ละตัวได้น้อยกว่า, มีค่าใช้จ่าย
  รายนาทีต่อเนื่อง, และเพิ่ม dependency ภายนอกอีกตัวในเรโปที่ปกติ self-host เอง
  (Bun/SQLite/Drizzle)
- **ประกอบ pipeline เอง** (ทำ WebRTC signaling เอง + streaming STT API + LLM +
  streaming TTS API แล้วต่อเข้าด้วยกัน): ควบคุม latency และต้นทุนตอน scale ได้มากกว่า
  เข้ากับแนวทาง "self-host เมื่อสมเหตุสมผล" ของเรโปนี้ Trade-off: งาน integration
  ตอนต้นเยอะกว่ามาก (ต้องต่อ 4 service ให้ถูกต้อง โดยเฉพาะเรื่อง barge-in) ก่อนจะมี
  demo ที่ใช้งานได้ตัวแรก

คำแนะนำสำหรับ spike แรก: ประเมินแพลตฟอร์มสำเร็จรูป 1 ตัวเทียบกับ pipeline ที่ประกอบเอง
แบบ OpenAI Realtime-style (หรือเทียบเท่า) บน scenario เดียวกันแบบ scripted แล้วเลือก
จากการวัด latency จริง + ดูว่าตัวเลือกสำเร็จรูปประหยัดคุ้มกับต้นทุน/การผูกมัดแค่ไหน

## หมายเหตุเรื่อง Runtime (เทียบกับข้อกำหนด Bun ใน CLAUDE.md)

CLAUDE.md ระบุให้ใช้ Bun ≥1.2 สำหรับ service ใหม่ สำหรับส่วน glue/orchestration ของ
pipeline นั้น Bun ใช้ได้และเป็นตัวเลือกหลัก แต่สำหรับตัว real-time audio transport เอง
อย่าฝืนใช้ Bun อย่างเดียวถ้า stack WebRTC media-server ที่เป็นผู้ใหญ่แล้ว (เช่นแบบ
LiveKit/Pion/mediasoup ซึ่งเอียงไปทาง Node/Go) พร้อมใช้งานจริงมากกว่าอย่างมีนัยสำคัญ
สำหรับเรื่อง jitter buffering และ audio routing — ถ้าเกิดกรณีนี้ให้ระบุไว้ชัดเจนต่อ
ไฟล์/service แทนที่จะเบี่ยงจาก convention แบบเงียบๆ

## คำถามสำคัญที่ต้องให้คนตัดสินใจ

- V1 ต้องมีเบอร์โทรจริงไหม หรือแบบเบราว์เซอร์อย่างเดียวรับได้สำหรับผู้ใช้กลุ่มแรก?
  (แผนนี้สมมติว่าเบราว์เซอร์อย่างเดียว — ยืนยันก่อนเริ่มหา vendor telephony ใดๆ)
- เมื่อ pipeline ล้มเหลวกลางสาย (STT ล่ม, LLM error, TTS พัง): วางสายอย่างสุภาพพร้อม
  คำขอโทษด้วยเสียง, ลองใหม่เงียบๆ หนึ่งครั้ง, หรือทำอย่างอื่น? V1 ไม่มีการโอนสายไปคนจริง
  — รับได้ไหม?
- ข้อกำหนดด้าน accessibility นอกเหนือจาก "เสียงล้วน ไม่ต้องมี UI ภาพ" — เช่น caption
  สำหรับผู้บกพร่องทางการได้ยินที่แสดงคู่กับสาย, เบราว์เซอร์/อุปกรณ์ขั้นต่ำที่รองรับ?
- ใครรับผิดชอบค่าใช้จ่ายรายนาทีของ vendor ถ้าเลือกแพลตฟอร์มสำเร็จรูป และมี cap
  การใช้งานสำหรับ V1 ไหม?
- เสียงการโทร (ถ้ามี) จะถูก log/เก็บไว้ที่ไหน นานแค่ไหน — ใครรับผิดชอบเรื่อง
  privacy/compliance?
- Route/ส่วนไหนใน `web/` (หรือแอปใหม่) จะเป็นที่อยู่ของปุ่ม "โทร" — sub-project ใหม่
  แบบ `web-shop/` หรือฟีเจอร์ในแอปที่มีอยู่แล้ว?

## Milestone แรก ("เสร็จ" สำหรับชิ้นเล็กสุดที่ใช้งานได้)

คุยแบบมี script ได้ **1 หัวข้อ ครบ end-to-end ในเบราว์เซอร์** — กดปุ่ม "โทร", พูดคำถาม
เกี่ยวกับหัวข้อที่กำหนดไว้, ได้ยินคำตอบเป็นเสียง, ขัดกลางคำตอบได้ 1 ครั้งแล้ว agent หยุด
และฟัง — โดย latency แบบ round-trip อยู่ที่หรือต่ำกว่าเป้า ~1.5 วินาที วัดและบันทึกไว้
อย่างน้อย 5 ครั้งติดต่อกันในการทดสอบ ยังไม่ต้อง harden สำหรับ production, ไม่ต้องมี
auth, ไม่ต้องมี persistence — แค่พิสูจน์ว่า pipeline ทำงานร่วมกันได้จริง และงบ latency
เป็นไปได้จริง
